# 战锤 40,000 LLM 终端文字游戏——产品与技术设计文档

> 文档状态：v1.1（工程开发交接基线；资料模式已冻结为 Public Baseline）  
> 文档日期：2026-09-01  
> 项目阶段：仅规划，尚未实现  
> 暂定项目名：**Noosphere: A 40K Chronicle / 诺斯菲尔纪事**

## 1. 项目目标

制作一款在终端中运行、由 LLM 驱动叙事、由确定性规则引擎负责数值与检定的单人文字角色扮演游戏。游戏必须满足：

1. 故事、人物、势力、地点、技术、历史与用语均处于战锤 40,000 世界观内。
2. 世界观事实只能来自经过登记和审核的资料，重要事实可追溯到具体来源，不能依赖 LLM 参数记忆“补全”。
3. 具备角色属性、技能、物品、任务、关系、时间、检定、战斗、伤势、资源与存档系统。
4. 支持预设剧本和自定义开局。
5. 面向不了解战锤 40K 的玩家，提供按需解释、术语提示、背景回顾和选择后果预览。
6. 玩家默认从帝国普通孩童时期开始，在家庭、教育、职业、服役、危机、衰老与死亡中逐步认识世界观。
7. 第一版以可靠、可审计、可扩展为优先，界面保持简洁。

成功标准不是“LLM 能讲一个像 40K 的故事”，而是“系统能证明关键设定来自哪里，并且 LLM 无权篡改规则结果、角色数据和已确认的世界事实”。

## 2. 设计原则

### 2.1 事实与叙事分离

- **资料库决定什么是真的**：世界设定、历史事件和已有角色关系来自审核后的 Lore Corpus。
- **规则引擎决定发生了什么**：随机数、检定、伤害、资源消耗、时间推进、任务状态均由程序计算。
- **LLM 决定如何讲述**：把检索到的事实和规则结果转换为场景、对白与可选行动。
- LLM 输出只能提交“变更提案”；只有通过模式校验和规则校验后，才能写入游戏状态。

### 2.2 默认锁定正史

- 默认开启 `Canon Lock`，禁止引入战锤 40K 之外的事物，也禁止把玩家的自由描述直接当成既定事实。
- 自定义开局必须选择或推断年代、区域、阵营、身份与事件尺度；无法兼容正史时，系统给出可兼容的改写建议。
- 可在未来加入明确标记的 `What-if` 模式，但该模式不属于第一版，也不能污染正史资料层。

### 2.3 可追溯而非伪权威

- 重要人物、事件、势力关系、地点归属、年代、技术限制等事实必须具有 `source_id`。
- 无来源、来源冲突或检索置信度不足时，系统必须降低叙事确定性、回避断言，或暂停并提供玩家选择；不得编造引用。
- “官方作品中的角色说法”不自动等于客观事实。需区分编辑性设定、小说中的有限视角和帝国宣传等不可靠叙述。

### 2.4 版权与可分发性

- 不随项目分发 Codex、小说、规则书或其他受版权保护作品的全文。
- 公共网页仅保存必要的事实摘要、短引用、来源 URL、访问时间及出处定位；遵守站点条款。
- 玩家合法拥有的电子书/PDF可选择在本地建立私人索引，但原文不得提交到仓库或上传到第三方服务。
- 游戏使用原创简化规则，不复制现有战锤桌面 RPG 的规则文本、表格或大段专有表达。
- 正式公开发布前，需要完成 Games Workshop 知识产权与 Fan Content Policy 的专项审核；不得暗示本项目由 Games Workshop 背书。

## 3. 第一版范围

### 3.1 必须具备（MVP）

- Python 终端应用，支持 Windows、Linux 和 macOS。
- 新游戏、继续游戏、自动保存、手动保存、存档列表与导出。
- 一个经过完整资料审核的“垂直切片”区域与年代，而非一开始覆盖全银河。
- 至少 3 个预设开局模板，以及受约束的自定义开局。
- 从孩童期到死亡/生命终局的阶段式成长系统；允许因战争、疾病、事故或选择提前死亡。
- 角色创建、属性、技能、装备、队友/关键 NPC 关系。
- 通用 d100 检定、对抗检定、战斗、伤势、死亡/失败处理。
- 任务日志、地点、游戏内时间、阵营声望/怀疑度等状态。
- 新手解释模式、术语表、`为什么？`、`我知道什么？`、`回顾`命令。
- 基于审核资料库的检索增强生成（RAG），叙事记录事实引用。
- 开发/审计模式下可查看本回合使用的资料和规则计算过程。
- 支持至少一种云端 LLM 接口，同时预留本地 OpenAI-compatible 接口。

### 3.2 第一版不做

- 全银河、全时代、全阵营的完整可玩内容。
- 多人联机、图形界面、语音、图像生成。
- 自由训练或微调模型。
- 自动从任意 Wiki 抓取并直接视为正史。
- 完整复刻桌面战棋或任何一套官方/授权桌面 RPG 规则。
- 让 LLM 直接读写存档或自行生成随机数。

### 3.3 建议的垂直切片

首版选择一个地域明确、社会结构完整、资料边界可控的生命历程场景：

**玩家出生在大裂隙之后某个正史兼容的原创帝国边疆星系，从普通孩童成长为帝国社会的一员，并最终迎来死亡或其他生命终局。**

原创星系、行星、家庭和大多数本地 NPC 必须标记为 `game_original`，其政治制度、宗教生活、科技边界、帝国机构及银河背景则由权威资料约束。这样既能让玩家真实改变自己的人生，又不会修改知名正史事件。正式名称必须通过资料库同名冲突扫描后确定。

默认完整生命阶段：

1. **幼年（约 6–11 岁）**：家庭、居住区、食物、劳动、信仰和帝国最基础的符号；以关系、观察和简单选择为主。
2. **少年（约 12–16 岁）**：教育、教会训导、职业筛选、同龄关系和第一次制度性选择。
3. **青年（约 17–25 岁）**：正式职业、服役、迁移、爱情/伙伴关系、第一次重大危机。
4. **壮年**：职业与阵营路线深化，可进入行政、军务、技术、医疗、商贸、执法或审判庭外围等路线。
5. **晚年/终局**：衰老、伤病、继承、信仰与过往选择结算；也可能在此前因世界事件提前死亡。

年龄只是普通帝国人类默认值。不同世界的历法、寿命、亚空间航行时间差、低温休眠和延寿技术必须按资料与角色阶层调整。

预设童年出身建议：

1. **巢都工人家庭**：从配给、工班、教会与巢都阶层认识帝国日常生活。
2. **虚空船员家庭**：从舰船共同体、机械维护与亚空间航行禁忌认识银河交通。
3. **行政/教会附属孤儿院**：从文字、档案、信仰和机构选拔认识帝国官僚体系。

以上仅为题材提案；进入内容制作前必须完成“资料充分性审查”。

## 4. 权威资料体系

### 4.1 来源分级

| 等级 | 来源类型 | 用法 | 能否单独支持关键事实 |
|---|---|---|---|
| A1 | Games Workshop 当前官方设定页、Codex、核心规则书、官方战役书 | 世界硬事实与时间线主依据 | 可以，但仍需记录版本与页码 |
| A2 | Black Library 小说/有声作品、官方短篇 | 人物、地点、文化与事件细节；标注叙事视角 | 可以，但主观陈述不得当作全知事实 |
| A3 | 官方授权 RPG、电子游戏及其资料 | 补充局部生活、装备和地点细节 | 需标注授权作品及连续性差异；关键冲突需 A1/A2 复核 |
| B | Lexicanum 等具有逐条来源标注、编辑规则明确的二级百科 | 定位原始出处、建立候选实体与关系 | 原则上不单独支持核心事实，应回查其引用 |
| C | 其他高质量二创文章、播客、视频、论坛考据 | 发现线索、理解争议 | 不进入事实库，除非能回溯至 A 级来源 |
| 禁用 | 无引用 Wiki 段落、搜索摘要、短视频口述、模型记忆、随机帖子 | 不使用 | 否 |

“权威二创”只作为带路索引，不因流行度或搜索排名成为真相来源。若原始资料暂时不可核验，该条目状态只能是 `unverified`，不能注入正式剧情。

### 4.2 首批官方入口（待逐项人工核验）

- Warhammer 40,000 官方世界介绍：<https://warhammer40000.com/the-setting/>
- Warhammer Community：<https://www.warhammer-community.com/>
- Warhammer 官方商店与出版物目录：<https://www.warhammer.com/>
- Black Library：<https://www.blacklibrary.com/>
- Warhammer Vault（仅在合法订阅与条款允许范围内使用）：<https://warhammer-vault.com/>
- Lexicanum（仅作为二级索引）：<https://wh40k.lexicanum.com/wiki/Main_Page>

这些 URL 不是“资料已验证”的证明。内容团队必须登记具体作品、版本、出版时间、章节/页码、适用年代、摘要和冲突说明。

### 4.3 资料登记结构

每个资料源至少记录：

```yaml
source_id: GW-CODEX-EXAMPLE-EDITION-PAGE
title: "作品完整标题"
publisher: "Games Workshop / Black Library / 授权方"
source_class: "A1 | A2 | A3 | B"
edition: "版本或版次"
publication_date: "YYYY-MM-DD 或 YYYY"
language: "en | zh | ..."
locator: "页码、章节、URL 锚点或时间码"
access_type: "public_web | local_owned_copy | metadata_only"
canon_scope: "适用时代、地域、阵营"
viewpoint: "editorial | in_universe | character_limited"
license_notes: "能否缓存、引用和分发"
review_status: "candidate | reviewed | rejected | superseded"
reviewed_by: "人工审核者"
reviewed_at: "时间"
```

每条可供游戏使用的事实记录：

```yaml
fact_id: "唯一 ID"
claim: "最小化、单一含义的事实陈述"
entities: ["实体 ID"]
relations: ["关系类型"]
valid_time: "事实在世界内的有效时期"
valid_region: "适用范围"
source_refs: ["source_id + locator"]
confidence: "confirmed | disputed | perspective_only"
conflicts_with: ["fact_id"]
spoiler_level: 0
review_status: "approved"
```

### 4.4 冲突、改版与“不可靠叙述者”

- 不采用简单的“较新出版物永远覆盖较旧出版物”。先判断是否为明确改版、不同历史阶段、不同角色视角或刻意保持神秘。
- 冲突事实并存，附 `valid_time`、`edition`、`viewpoint` 和 `conflicts_with`。
- 叙事时只取与当前年代和玩家认知相容的事实。
- 对官方有意模糊的内容，叙述为传闻、教义、报告或争议，不给出虚假的唯一答案。
- 玩家角色的知识不等于资料库的全知知识；需经过 `knowledge_filter` 再交给叙事模型。

### 4.5 资料生产流水线

1. **选定内容边界**：年代、地域、涉及阵营、主题。
2. **建立来源清单**：优先 A1/A2，B 级仅帮助定位。
3. **合法获取**：登记公共页面或玩家合法拥有的本地文档。
4. **解析与切块**：保留标题、章节、页码、上下文和版本元数据。
5. **实体对齐**：人物、组织、地点、事件、物品分配稳定 ID 与别名。
6. **事实抽取**：模型可提出候选事实，但不得自动批准。
7. **人工双重审核**：设定正确性审核 + 来源/授权审核。
8. **关系图构建**：记录人物—组织—事件—地点及时间有效性。
9. **检索测试**：为每个剧情主题建立事实问答与反幻觉测试集。
10. **内容冻结**：生成带版本号和哈希的 Lore Pack，存档记录使用版本。

### 4.6 “资料要全”的可执行定义

战锤 40K 资料规模巨大且持续更新，“收齐整个世界观”既不可现实交付，也无法保证合法分发。因此将完整性定义为：

- 对**当前可玩内容边界**内的所有人物、势力、地点、历史前置、装备与关键术语，资料覆盖率达到 100%。
- 每个主线场景所需的关键事实均至少有一个 A 级出处。
- 每个关系和历史断言都有来源定位或被明确标记为游戏原创角色/游戏过程中新产生的事件。
- 超出内容边界的问题可以解释为“当前资料包未覆盖”，不得靠模型补写。
- 后续以版本化 Lore Pack 扩展新区域、新年代和新阵营。

为了兼顾玩家希望获得的广泛科普与剧情可靠性，资料按两层交付：

- **Galaxy Primer（广覆盖百科层）**：覆盖 40K 的核心时间线、银河地理、帝国主要机构、混沌、亚空间、主要异形阵营、重要战争与基础术语。目标是“主要概念不缺席”，但不宣称穷尽全部出版物。
- **Campaign Canon Pack（深覆盖剧情层）**：覆盖本次生命历程会实际接触的制度、职业、装备、地点类型、阵营关系和历史前置。只有此层达到审核门槛的内容才可驱动剧情。

百科层条目不能因为存在于数据库中就自动成为玩家角色的知识，也不能在缺少剧情层细节时被 LLM 扩写成具体事件。

### 4.7 资料不足时的安全降级

资料不足本身不可避免，危险的是让模型把空白误当成创作授权。系统必须先把待生成内容分为四类：

| 内容类型 | 示例 | 资料要求 | 资料不足时的行为 |
|---|---|---|---|
| 正史硬事实 | 年代、阵营归属、历史事件、人物关系、技术限制 | 必须有批准的 `fact_id` | 禁止断言；改为提示未覆盖、重新检索或缩小问题 |
| 世界内观点 | 某角色的信念、传闻、帝国宣传 | 必须注明说话者和视角 | 可以作为传闻呈现，但不得伪装成客观事实 |
| 本作原创事实 | 原创 NPC、房间布局、局部案件、当前战役事件 | 必须通过年代、地点、阵营和技术约束校验 | 可生成，写入 `game_original` 命名空间并明确标识 |
| 装饰性叙述 | 气味、光线、动作和不改变设定的氛围 | 不要求逐句引用 | 可生成，但不得夹带新的历史、组织或技术断言 |

每次生成前执行 `Lore Coverage Gate`：

1. 从玩家意图和候选场景中提取需要回答的实体、关系、年代与技术断言。
2. 检查当前 Lore Pack 是否覆盖相应实体和时空范围。
3. 关键断言只有在检索到批准事实后才能进入 LLM 上下文。
4. 覆盖不足时，不要求 LLM“尽量回答”，而是选择安全降级：
   - 角色合理地表示不知道或资料残缺；
   - 向玩家说明当前内容包未覆盖；
   - 建议切换到已支持的地点、年代或身份；
   - 仅生成不影响正史的局部原创内容。
5. 生成后再次抽取 Lore 断言，与输入的 `fact_id` 和允许的原创实体逐条比对。
6. 未通过检查的文本不展示、不写入事件日志；最多自动修复一次，仍失败则使用程序模板输出。

系统不能承诺从概率意义上彻底消灭模型幻觉，但必须保证：**未经来源支持或原创规则授权的关键断言，不能成为游戏事实、不能改变状态，也不能进入正式存档。**

## 5. 系统架构

```text
玩家输入
   │
   ▼
命令解析 / 意图识别
   │
   ├── 元命令 ──────────────► 存档、帮助、词条、设置
   │
   ▼
行动提案与规则预检
   │
   ├── 需要事实 ────────────► Lore 检索 ─► 来源/时代/玩家知识过滤
   │
   ├── 需要检定 ────────────► 确定性规则引擎 ─► 骰点与状态变更提案
   │
   ▼
叙事上下文组装器
   │  （只包含获准事实、可见状态、规则结果和内容设置）
   ▼
LLM 生成结构化回合输出
   │
   ▼
Schema 校验 + Canon Guard + 状态变更白名单
   │
   ├── 失败：自动修复一次 / 降级模板输出
   ▼
事件日志写入 ─► 原子存档 ─► 终端渲染
```

### 5.1 建议技术栈

- Python 3.12+
- CLI：首版使用 `Typer` + `Rich`；若后续需要完整 TUI，再迁移 `Textual`
- 数据模型与校验：`Pydantic`
- 存储：SQLite（结构化状态、事件日志、FTS5 全文检索）
- 向量检索：可插拔；小型 Lore Pack 可先用 BM25/FTS5，验证需要后再加本地 embedding
- LLM：Provider Adapter，兼容 OpenAI Responses/API 风格和本地 OpenAI-compatible 服务
- 配置：TOML；密钥仅通过环境变量或系统密钥环，不写入存档
- 测试：`pytest` + 固定随机种子 + LLM 录制/桩响应

不建议首版引入复杂 Agent 框架。单回合采用明确管线和 JSON Schema 更易测试、审计和控制成本。

### 5.2 主要模块

```text
src/
  cli/             # 命令、终端渲染、交互循环
  game/            # 回合、场景、任务、时间、规则
  rules/           # 检定、战斗、伤势、资源、随机数
  lore/            # 来源注册、检索、关系图、知识过滤
  llm/             # Provider、提示词、结构化响应、重试
  canon_guard/     # 实体验证、年代验证、断言与引用检查
  saves/           # 快照、事件日志、迁移、备份、导入导出
  onboarding/      # 新手解释、术语、回顾与提示
content/
  lore_packs/      # 仅可分发的事实摘要和元数据
  scenarios/       # 审核后的场景、任务、NPC、遭遇
  glossary/        # 分层术语解释
tests/
docs/
```

## 6. 回合与叙事协议

### 6.1 标准回合

1. 展示场景、可见角色、紧迫状态与建议行动。
2. 玩家输入自然语言或终端命令。
3. 解析成一个或多个 `ActionIntent`。
4. 检查行动是否可行、是否需要资料、资源或检定。
5. 若玩家不清楚风险，先给简短风险提示；明显不可逆行动要求确认。
6. 规则引擎完成所有随机与数值计算。
7. 检索与该回合相关且玩家有资格知道的事实。
8. LLM 基于固定输入生成场景文本和结构化提案。
9. 校验提案，写入事件日志与快照。
10. 展示结果、状态变化、可选动作和按需术语解释。

### 6.2 LLM 输出契约（示意）

```json
{
  "narration": "面向玩家的叙事文本",
  "dialogue": [],
  "suggested_actions": [],
  "proposed_events": [
    {"type": "relationship_delta", "target_id": "npc_x", "value": -1, "reason": "..."}
  ],
  "lore_claims": [
    {"claim": "...", "fact_ids": ["fact_x"]}
  ],
  "glossary_terms": ["term_id"],
  "uncertainties": []
}
```

`narration` 不被当作状态。`proposed_events` 只允许使用注册过的事件类型，并由规则引擎二次验证。

### 6.3 反幻觉护栏

- 提示词明确禁止模型使用上下文外的 40K 事实。
- 所有真实世界观实体必须解析到 `entity_id`；临时原创 NPC 使用独立命名空间并记录生成规则。
- 关键 Lore 断言必须关联 `fact_id`，不能只给看似可信的书名。
- 对回合文本执行实体、年代、阵营归属和技术可用性检查。
- 不允许模型伪造骰点、奖励、物品、任务完成或人物死亡。
- 一次结构化修复仍失败时，使用程序模板描述规则结果，并保存错误供审计。
- 开发模式显示：检索片段、来源等级、过滤原因、骰点、修正值和最终状态差异。

### 6.4 幻觉处置级别

- **L0 装饰偏差**：不涉及事实和状态的措辞问题，可保留或在后续润色。
- **L1 未支持细节**：出现没有来源的组织、装备细节或历史暗示；整段丢弃并重新生成。
- **L2 正史冲突**：年代、人物、阵营或技术发生冲突；阻止回合提交，记录测试样本。
- **L3 状态越权**：模型伪造骰点、物品、死亡、任务或关系变化；立即拒绝响应并使用确定性模板完成回合。
- 同类 L1–L3 错误反复出现时，自动降低模型可用上下文和生成自由度；不得通过“让模型自我确认正确”代替程序校验。

## 7. 原创简化 d100 规则

本规则只借鉴百分骰 RPG 的通用思想，具体数值、术语和表格需原创并经平衡测试。

### 7.1 核心属性

- 近战（Melee）
- 射击（Ranged）
- 体魄（Body）
- 敏捷（Agility）
- 学识（Intellect）
- 感知（Awareness）
- 意志（Willpower）
- 交涉（Presence）

典型普通人属性约为 25–45；受过训练者的专长可更高。超人类单位不能只靠把普通人属性无限放大，需要体型、护甲、武器等级和特性共同建模。

### 7.2 通用检定

```text
目标值 = 属性 + 技能加值 + 难度修正 + 情境修正
掷 1d100；点数 <= 目标值则成功
成功/失败幅度 = floor(abs(目标值 - 点数) / 10) + 1
```

- 极易到近乎不可能的难度修正采用有限档位。
- 对抗检定先比较成功与否，再比较成功幅度，最后比较相关属性。
- 暗骰由引擎执行，玩家只看到角色能感知的结果。
- 随机源、种子、所有修正和结果写入事件日志，可完整复盘。

### 7.3 资源与长期状态

- 生命/伤势：轻伤、重伤、危重和永久后果；避免单一 HP 造成的失真。
- 压力：恐惧、疲劳、创伤与暂时失控。
- 腐化：接触亚空间或禁忌造成，变化必须有明确事件依据。
- 命运点：少量、珍贵，用于重掷或避免一次灾难性后果。
- 补给：弹药、医疗、金钱/配给、权限与交通资源。
- 阵营关系：信任、义务、怀疑、敌意分别记录，不能压缩成单一好感度。
- 认知状态：玩家角色已知、怀疑、误信和未知的信息分开保存。

### 7.4 战斗

- 回合制，动作经济保持简洁：移动、主要行动、反应和少量自由行动。
- 命中由射击/近战检定决定；伤害、护甲、穿透、掩体和伤势由引擎计算。
- 敌人使用行为模板和目标优先级；LLM 只描述战术，不决定合法动作或伤害。
- 支持撤退、投降、压制、谈判和环境利用，避免所有冲突都变成杀戮。
- Boss 和阿斯塔特等高阶单位使用阶段、特性与叙事权限限制，保持世界观尺度。

### 7.5 失败前进

普通失败应改变局势而非总是卡死：耗费时间、暴露身份、损失资源、得到不完整线索、形成债务或令敌人先行动。只有明确的高风险场景才直接导致死亡或战役结束。

### 7.6 年龄、成长与生命终局

- 游戏时间同时支持逐日回合与阶段跳跃。重要场景逐回合游玩，平静年份通过经玩家确认的 `Life Transition` 汇总。
- 属性不能随升级无限增长。孩童期主要形成倾向、关系和基础能力；青年期增长最快；壮年趋于稳定；晚年可能获得学识与影响力，同时体魄、反应或健康下降。
- 技能来自实际经历、教育和职业，不能只靠抽象经验值购买。
- 每次阶段转换结算：年龄、身体变化、家庭状态、职业、居所、关系、知识、创伤、资产、债务和世界时间。
- 死亡不只是一条 HP 归零规则。战斗、事故、疾病、腐化、处决、衰老和自我牺牲均可形成不同终局。
- 终局生成带来源区分的《一生纪事》：官方背景、原创人物经历、玩家选择和规则结果分别标识。
- 默认允许读取死亡前自动存档，但“纪事模式”可选择死亡不可撤销；铁人模式不属于 MVP 强制要求。

## 8. 角色、NPC 与关系网

### 8.1 玩家角色

记录：出生时间、实际年龄、主观年龄、出身、监护人、家庭阶层、教育、职业角色、阵营归属、信条、秘密、属性、技能、特性、装备、伤势、资源、知识、个人目标和遗产。

角色创建采用“童年出身模板 + 少量定制”以兼顾新手：

1. 选择出生环境、家庭/监护关系和生活条件，而不是直接选择成年职业。
2. 系统只解释孩童当下能理解的世界，并提供可切换的玩家百科说明。
3. 选择性格倾向、兴趣、恐惧和一项家庭关系；初始属性由出身、选择和少量点数共同形成。
4. 成年职业由成长过程、能力、关系、制度分配和玩家选择共同决定。
5. 灵能、变种、贵族、军务或特殊机构路线必须由相应内容包和事件解锁，不能在资料不足时自由声明。

### 8.2 NPC

- **正史 NPC**：只能使用资料库确认的信息；模型无权改变其基础身份和既定历史。
- **审核原创 NPC**：由内容作者预先制作，可担任长期角色。
- **临时生成 NPC**：必须符合地点人口、机构层级和命名规则；晋升为重要 NPC 时冻结其资料。
- NPC 的目标、恐惧、资源、职责、对玩家的认知与关系分别建模。

### 8.3 关系图

关系至少包含：主体、客体、关系类型、方向、强度、公开性、起止时间、来源及当前证据。关系类型包括隶属、敌对、盟约、血缘、债务、秘密控制、怀疑、共同经历等。

正史关系和游戏过程产生的关系分层存储。后者来自事件日志，不能被误标成官方设定。

## 9. 自定义开局

### 9.1 两种入口

**引导式创建（推荐给新手）**

- 年代：只展示已安装 Lore Pack 支持的选项。
- 地区：星区/星系/行星或舰船。
- 童年出身：家庭、孤儿院、舰船共同体或其他内容包支持的监护环境。
- 社会位置：居住层级、家庭职业、物质条件与可获得的教育。
- 主题偏好：成长、家庭、调查、生存、军事、政治、探索、恐怖。
- 起始年龄：默认约 8 岁；内容包可提供其他合理年龄。
- 叙事尺度、黑暗程度、战斗频率和解释密度。

**自然语言创建**

玩家输入想法后，LLM 只能将其解析为约束；`Opening Validator` 负责：

1. 检查是否完全属于 40K 世界。
2. 检查年代、地点、阵营、身份和技术是否互相兼容。
3. 检查当前 Lore Pack 是否覆盖。
4. 标出冲突和缺口，并给出最多三个最接近的正史兼容方案。
5. 生成可审核的 `Campaign Seed`，经玩家确认后才创建存档。

### 9.2 Campaign Seed

```yaml
era: "受支持的明确时间范围"
region_id: "地点实体 ID"
player_faction_id: "阵营实体 ID"
role_template_id: "角色模板"
start_age: 8
lifepath_mode: "full_life"
themes: ["investigation", "survival"]
tone: "grim | balanced | heroic-but-costly"
power_scale: "human"
content_limits: []
required_lore_packs: []
canon_validation: "passed"
validation_evidence: []
opening_hook: "仅描述获准事实与原创冲突"
```

“自定义”指在已验证的 40K 约束内组合开局，不意味着允许现代地球、跨作品角色或与已选年代矛盾的设定。

## 10. 新手引导与知识提示

### 10.1 三层解释

- **剧情内学习**：通过家人、教师、教会人员、工头和亲历事件，以角色年龄能够理解的方式认识世界。
- **即时提示**：术语首次出现时，用一句不打断节奏的玩家层解释。
- **按需展开**：输入 `百科 <术语>` 或选择编号，查看 100–300 字解释、玩家角色是否知道、来源标签。
- **深度背景**：查看时间线、阵营关系和相关事件；默认隐藏剧透与角色不应知道的事实。

剧情内解释和玩家百科必须视觉区分：前者可能带有帝国宣传、地方偏见或角色误解；后者以中立、带来源的方式说明“这是世界内观点还是编辑性事实”。

### 10.2 新手命令

```text
帮助                  显示当前可用命令
建议                  给出 3–5 个符合角色认知的行动，并解释风险
为什么 <内容>         解释规则或世界观原因
百科 <术语>           查看无剧透词条
我知道什么 <主题>     仅按角色知识回答
关系                  查看已知人物/阵营关系
回顾                  生成近期剧情与未完成目标摘要
检定详情              展示上一检定的骰点和全部修正
来源                  展示上一回合使用的设定来源
设置 教学 简洁|标准|详细
```

### 10.3 选项呈现

LLM 每回合提供建议但不限制自由输入。每个建议可带短标签：`[安全]`、`[需检定]`、`[高风险]`、`[消耗资源]`、`[可能违法/异端]`。风险提示基于角色可知信息，不能泄露隐藏敌人或剧情答案。

## 11. 存档与可复现性

### 11.1 存储策略

- SQLite 为主存档，每个战役一个数据库文件或一个数据库中的隔离 campaign。
- **事件溯源 + 周期快照**：所有状态变化写成不可变事件；每 N 回合创建快照以快速加载。
- 每回合事务提交，先写临时文件/事务后原子替换，防止中断损坏。
- 保留最近若干自动备份，支持从最后一个校验通过的快照恢复。
- 导出为 ZIP：数据库、配置、已安装内容包清单、必要摘要和校验和；不包含 API key 或受版权保护原文。

### 11.2 存档必须记录

- 存档 Schema 版本、游戏版本、规则版本。
- Lore Pack ID、版本、哈希和引用快照。
- LLM provider/model 标识、提示模板版本；不强求同模型重放出相同文案。
- 随机种子、每次骰点、全部修正。
- 玩家输入、解析出的意图、获准事件、状态 diff。
- 角色、NPC、地点、任务、关系、时间、资源、知识与内容设置。
- 角色年龄、生命阶段、教育/职业履历、家庭谱系、重大人生节点和终局状态。
- 可选的叙事文本和 token/成本统计。

### 11.3 兼容与迁移

- 任何 Schema 变化必须有单向迁移脚本和迁移前备份。
- Lore Pack 更新不能静默重写进行中的战役；玩家可保持原版本或执行带报告的升级。
- 缺少旧内容包时允许只读打开和导出，不应直接损坏存档。

```text
┌─ 幼年纪 · 8 岁 · 配给日 06:40 ───────────────────┐
│ 地点：工人居住层         状态：饥饿 / 好奇         │
│ 当前目标：跟随母亲前往工班登记处                   │
└──────────────────────────────────────────────────┘

广播里的晨祷被机器轰鸣切成断断续续的句子。母亲让你
低下头，不要盯着巡过长廊的红袍人看。

[术语·玩家层] 红袍人可能属于机械教相关人员。你的角色目前只知道他们负责机器。

1. 小声问母亲他们是谁   [安全 / 学习]
2. 观察红袍人的工具     [需检定：感知，低风险]

```

默认只显示结果所需信息；`检定详情`和`来源`可展开审计信息。所有颜色都有纯文本替代，支持无颜色终端和屏幕阅读器。

## 13. 内容与安全设置

战锤 40K 包含宗教极权、战争、身体恐怖、奴役、酷刑、种族灭绝和精神污染等成人主题。游戏首次启动需让玩家选择内容强度：

- 描写强度：淡出、适中、强烈。
- 可单独关闭的主题标签。
- 随时使用 `暂停`、`跳过场景`、`内容设置`。
- 不能把帝国或其他阵营的宣传作为现实世界价值判断；新手解释需区分“世界内立场”和“设计文档的中立描述”。
- 不用现实族群、宗教或政治对象替换 40K 虚构敌人，不生成针对现实受保护群体的仇恨内容。
- 玩家角色未成年期间禁止任何情色或性化内容，恋爱系统仅在角色达到内容包规定的成年阶段后开放。
- 幼年阶段默认采用非图形化暴力描写；严重伤害、虐待和死亡可以淡出，并由内容设置进一步关闭。
- 不把对孩童的伤害作为廉价冲击手段；相关场景必须服务于明确主题、允许跳过，并经过内容审核。

## 14. LLM 与成本策略

- Provider 可配置，模型不写死；能力检测包括结构化输出、上下文长度和工具调用支持。
- 每回合上下文只装载：最近事件摘要、当前场景状态、相关关系、检索事实与规则结果。
- 长期历史由程序生成分层摘要，但关键事件始终保留结构化记录，防止摘要漂移。
- Lore 检索结果缓存；静态介绍优先使用审核模板，减少重复调用。
- 设置每回合最大 token、重试次数和费用上限；达到上限时降级为简短叙事或模板输出。
- 密钥不得出现在日志、错误报告和导出存档中。

## 15. 测试与验收

### 15.1 规则测试

- 同一状态、输入和随机种子产生完全相同的检定与状态变化。
- 边界目标值、暴击/灾难结果、对抗、护甲、伤势、死亡和资源不足均有单元测试。
- LLM 试图修改骰点或提交越权事件时被拒绝。

### 15.2 Lore 与 Canon 测试

- Galaxy Primer 建立至少 500 个核心概念问答；Campaign Canon Pack 建立至少 200 个深度问答，覆盖正确事实、年代陷阱、同名实体、争议事实和无资料问题。
- 所有关键回答能追溯到批准的 `fact_id` 与 A 级出处。
- 向模型诱导不存在的军团、角色、科技或历史时，系统拒绝承认。
- 自定义开局中的跨年代和阵营矛盾能被识别并给出兼容改写。
- 玩家角色不知道的事实不能通过建议、术语或叙述意外泄露。

### 15.3 存档测试

- 在任意回合强制退出后，最多丢失当前未提交回合。
- 存档能校验损坏并从备份恢复。
- 旧 Schema 可迁移，失败时原文件不被覆盖。
- 导出文件不包含密钥和受版权保护的索引原文。

### 15.4 UX 验收

- 完全不了解 40K 的测试者能在 10 分钟内完成角色创建和首个有效行动。
- 完全不了解 40K 的测试者游玩幼年章节 30 分钟后，能够用自己的话解释帝国、帝皇、巢都/舰船生活和至少一个主要机构的基本含义。
- 首次出现的核心术语均有简短解释，且可关闭。
- 玩家能够理解一次检定为何成功或失败。
- 常用流程无需记忆命令；编号选择与自然语言均可用。

### 15.5 MVP 发布门槛

- 可完整经历幼年、少年、青年、壮年、晚年及死亡终局；主线目标时长调整为至少 8–12 小时，并具有至少四条职业路线和六种生命终局。
- 垂直切片 Lore 覆盖清单全部通过人工审核。
- 连续 100 回合压力测试无非法状态写入、存档损坏或无来源关键断言。
- 关键路径无联网也能加载存档、查看资料与运行规则；只有生成新叙事依赖所选 LLM。
- 法务/IP 检查清单完成，README 明确非官方性质与所需合法资料。

## 16. 实施阶段与审核门

### 阶段 0：范围与授权确认

产物：最终垂直切片、来源目录、可用性/授权矩阵、风险清单。  
审核门：至少一名熟悉 40K 的内容审核者确认范围有足够 A 级资料；未经此门不得写主线。

### 阶段 1：规则与存档原型

产物：无 LLM 的可玩 CLI、角色创建、d100 检定、战斗、事件日志、存取档。  
审核门：确定性、迁移和故障恢复测试通过。

### 阶段 2：Lore Pack 工具链

产物：来源注册、解析、事实审批、实体关系、检索、引用显示、Canon 测试集。  
审核门：垂直切片关键事实覆盖率 100%，无未经批准内容进入运行包。

### 阶段 3：LLM 叙事接入

产物：结构化回合协议、上下文组装、知识过滤、Canon Guard、降级策略。  
审核门：越权写入和幻觉诱导测试通过，关键事实引用率 100%。

### 阶段 4：内容与新手体验

产物：3 个开局、完整主线、术语表、教程、回顾、建议与内容设置。  
审核门：新手可用性测试与 40K 内容审核通过。

### 阶段 5：发布准备

产物：打包、配置向导、兼容测试、隐私说明、IP 声明、故障报告工具。  
审核门：MVP 发布门槛全部通过。

## 17. 主要风险与缓解措施

| 风险 | 影响 | 缓解 |
|---|---|---|
| 资料体量无限膨胀 | 永远无法完成 | 以版本化 Lore Pack 和可玩边界定义“全” |
| LLM 编造设定或引用 | 破坏可信度 | 事实白名单、claim 引用、Canon Guard、低置信度拒答 |
| 官方资料互相矛盾 | 得出错误唯一结论 | 保存版本、时代、视角和冲突，不强行合并 |
| 版权资料不可分发 | 无法发布 | 只分发可许可摘要/元数据；私有资料仅本地索引 |
| LLM 改写数值 | 存档失真 | 规则引擎唯一写入权，Schema 和事件白名单 |
| 长战役上下文漂移 | 人物失忆、关系跳变 | 结构化状态、事件溯源、分层摘要与引用 |
| API 成本/网络问题 | 无法持续游玩 | token 预算、缓存、本地 provider、模板降级 |
| 新手信息过载 | 难以上手 | 三层解释、按需展开、角色知识过滤 |
| 自定义开局越界 | 产生伪 40K 设定 | 只解析约束，由 Validator 和已安装内容包裁决 |

## 18. 已采纳的补充需求

以下需求建议纳入：

1. **审计模式**：随时查看上一回合事实来源、检定过程和状态变化。
2. **内容包版本锁定**：保证长战役不会因资料更新突然改写世界。
3. **离线规则模式**：无 LLM 时仍可浏览存档、人物、百科和执行确定性系统。
4. **可访问性**：无颜色模式、可调文本宽度、屏幕阅读器友好输出。
5. **隐私与费用控制**：发送给云端模型前展示数据范围，可设置每回合/每日费用上限。
6. **剧透级别**：词条和来源说明根据当前进度过滤。
7. **调试重放**：开发者可从任意事件快照复现规则错误。
8. **模组边界**：未来允许第三方 Scenario Pack，但必须标记 `official-sourced`、`licensed-derived` 或 `fan-original`，不能混淆来源。

## 19. 仍需外部确认的事项

以下事项不阻塞工程骨架开发，但会阻塞正式 Lore 内容冻结或公开发布：

1. 首个垂直切片的具体年代、星区/星球和参与阵营。
2. 可以合法获取并用于索引的首批 A 级资料清单。
3. 已确认不提供私人 Codex、规则书或 Black Library 资料；项目固定采用 Public Baseline，不得把书籍独有细节视为可用事实。
4. 首版实际启用的 LLM provider、默认模型和费用预算；架构必须同时兼容云端与本地 OpenAI-compatible 服务。
5. 具体官方作品版本、中文译名裁决者和至少一名 40K 人工 Lore 审核者。
6. 正式发布前的 IP/Fan Content Policy 审核结论。

## 20. 推荐结论

建议进入工程骨架开发，同时并行开展“阶段 0：范围、资料与授权确认”，但**不把整个 40K 宇宙作为首版可玩剧情范围**。正确的交付方式是：以 Galaxy Primer 尽量广泛地科普主要背景，以 Campaign Canon Pack 深度覆盖一个可追溯、8–12 小时可玩的完整人生垂直切片，并把 Lore Pack、规则引擎和存档建设为可扩展基础。这样既能兑现“权威、避免幻觉”的核心要求，也能让后续扩展新年代和阵营时保持同一质量标准。

## 21. 已批准的需求补充（2026-09-01）

审核者已同意将以下内容纳入正式需求基线：

1. “资料完整”以当前可玩边界为单位验收，通过版本化 Lore Pack 扩展，不以首版收录整个 40K 宇宙为目标。
2. 权威二创只用于发现出处，关键事实需回溯至官方或官方授权资料。
3. 官方资料冲突需要保存版本、年代和叙事视角，不强行制造唯一结论。
4. 采用“官方世界框架 + 审核后的原创局部剧情”；原创人物、地点、案件和游戏事件必须明确标识。
5. 自定义开局必须通过年代、地点、阵营、身份、技术和 Lore Pack 覆盖校验。
6. 不分发受版权保护资料全文，私人资料只允许在本地建立索引。
7. 核心循环确定为“调查线索—选择立场—承担检定与资源代价—改变关系和局势—推进危机”。
8. 首版以帝国普通孩童开局，经成长进入普通人到审判庭外围人员的权力尺度；高权力角色后续另行制作内容包。
9. 区分资料库全知、角色已知、角色怀疑/误信和玩家百科知识。
10. 对官方设定、授权作品、争议内容、本作原创和游戏过程产生的事实分别标识。
11. 允许透明的难度辅助，但禁止暗改骰点。
12. 关键线索支持失败前进，避免单次检定造成永久卡关。
13. 明确定义死亡、任务失败、腐化、阵营决裂、继任角色及回滚规则。
14. 建立中英双语术语、别名、旧译和社区常用译名对照。
15. 提供模型费用、云端隐私、本地模型、日志保存和服务失效降级设置。
16. 提供叙事长度、战斗比例、选项数量、解释密度和场景节奏设置。
17. 提供主题级内容过滤和淡出机制。
18. 进行中的存档锁定 Lore Pack 版本，更新不得静默改变战役。

当前推荐默认方案为：大裂隙之后的官方时代框架、符合设定的原创帝国边疆星系、约 8 岁普通人类孩童开局、经历幼年到死亡的完整生命历程、成长后可进入审判庭外围等职业路线、原创简化 d100、简体中文输出并为核心术语附英文、8–12 小时首条完整人生、三个童年出身与受约束的自然语言开局。资料采用“Galaxy Primer 广覆盖百科层 + Campaign Canon Pack 深覆盖剧情层”，前者负责全面科普，后者负责确保实际剧情不依赖模型编造。

## 22. 已批准的方向变更（2026-09-01）

1. 默认从孩童时期开始，逐步经历成长、职业、重大人生事件、衰老与死亡；提前死亡也是合法终局。
2. 世界观教学主要随生命经历逐层展开，使无 40K 基础的玩家可以通过生活经验建立理解。
3. 背景知识覆盖范围扩大为 Galaxy Primer，尽量涵盖主要时代、阵营、机构、战争和概念。
4. 广覆盖百科不降低事实标准；只有来源充分的 Campaign Canon Pack 内容才能驱动具体剧情。
5. 孩童阶段启用年龄适配内容限制，禁止情色/性化内容并默认降低图形化暴力描写。

## 23. 已确认的资料模式（2026-09-01）

用户确认不提供私人购买的 Codex、规则书或 Black Library 电子资料。MVP 固定使用 `Public Baseline`：

1. 只处理公开可访问且当时条款允许使用的官方网页、官方公开文章和可分发元数据。
2. 二级百科只用于发现原始出处和建立待核验清单，不能单独支持关键剧情事实。
3. 书籍、付费 Vault 或订阅内容中未在公开官方来源得到确认的细节一律视为 `uncovered`。
4. 背景空白通过正史兼容且明确标记的原创地方人物、地点和事件填充，不通过模型记忆补写官方设定。
5. Galaxy Primer 的“尽量全”指主要概念覆盖广泛，不代表收录全部出版物细节；每个条目仍需公开来源。
